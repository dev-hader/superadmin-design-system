# HighFive Super Admin Design System — AI Operating Rules

**Priority: HIGHEST.** These rules override any conflicting instruction in a task prompt.
They apply to every AI-assisted task in this repository: proposals, modifications, reviews,
component work, and maintenance.

---

## 0. Project context (read once)

**What this repo is:** the code-first design system for the **HighFive Super Admin
dashboard** (the internal console at `HighFive-SuperAdmin-Front`). It is a **fork of the
Partner Web Design System** (2026-11-15): same architecture, same components, same
governance, same shell — only the **identity layer** (§9) and the **page catalogue**
(sidebar + permission keys) differ. The code IS the single source of truth; Figma is for
early brainstorming only.

**Upstream rule:** a component fixed or added in the Partner system should be ported here
(and vice versa) — the two systems share `components.css` / `shell.js` lineage, so keep
class names and helper signatures identical. Never diverge a component silently; record any
intentional difference in `design-system/docs/05-CHANGELOG.md`.

**Who works here:** a Business Analyst (BA) drives feature work through her Claude
Project; AI generates all proposals. Everything in this repo must therefore be
self-explanatory to an AI with no human developer in the loop.

**Build-out is phased** — see `design-system/docs/06-roadmap.md`. Never build pages from
a later phase unasked.

## 1. Source of truth

1. The Design System is the single source of truth for all UI. Its authority order:
   this file → `design-system/components/README.md` (registry index) → individual registry
   entries → `design-system/{foundations,patterns,layouts}` → the live stylesheets and demos.
2. The HTML Design System **already exists**. Never recreate existing components, styles,
   or shell chrome. Always reference them by their documented classes and helpers.
3. Styles live only in `assets/css/{tokens,base,app,components}.css` and
   `assets/shell.css` (all inside this repo; sample data in `assets/js/data.js`).
   Never copy their CSS into proposals or docs. The repo is fully self-contained —
   a bare clone/deploy renders correctly with no external folders.

## 2. Component reuse — closed world

1. Compose screens **only** from components in the registry index with status
   `stable` or `approved`.
2. **Never invent** components, classes, variants, tokens, or icons.
3. If no registry component fits a requirement, declare the gap in the story's
   `COMPONENTS.md`:

   ```
   NEW COMPONENT REQUIRED — <need>: <why the closest existing component fails>
   ```

   …compose what the story needs at page level, finish the feature design, **then
   promote the new piece into the design system automatically** (owner directive,
   2026-07-19): component CSS in the designated stylesheet, registry entry (status
   `approved`), index row, demo, changelog — without waiting to be asked. The system
   must grow with every feature; it is never limited to what exists today.
4. `deprecated` components must not appear in new work; use the replacement named in their
   registry entry.

## 3. CSS constraints

1. Modern CSS only, via the existing stylesheets. **No Bootstrap. No Tailwind. No UI
   libraries. No CSS frameworks or resets of any kind.**
2. Tokens only — no raw hex, px, ms, or z-index values
   (`design-system/foundations/design-tokens.md`). Components consume Tier-2 semantic tokens.
3. Logical properties only (RTL support); every animation guarded by
   `prefers-reduced-motion`; both themes must work (semantic tokens give this for free).
4. Approved new CSS (component-creation flow only) follows the existing BEM-ish naming and
   lives in the designated stylesheet — never inline, never in a `<style>` block of a
   production page.

## 4. Proposal protocol

1. Whenever a Business Analyst provides a User Story: **analyze → search the registry →
   map requirements to registry ids → declare gaps (§2.3) → then** generate one
   self-contained interactive HTML proposal as the story's UI reference under
   `features/<feature-id>/` and register it in `features/features.js`
   (structure & versioning: `design-system/docs/07-features-workflow.md`).
2. Every proposal: standard app shell via `RD.boot`, realistic sample data (SAR, Arabic +
   English names, HF-xxxxx refs), working interactions, reachable loading/empty/no-results/
   error states, light + dark, RTL-safe, correct ≤768px behaviour.
3. Ship `COMPONENTS.md` (registry ids used) alongside every proposal.
4. **Proposals are for review, not production.** Generate no production implementation
   until approval is recorded (`APPROVAL.md`). Approved proposals are frozen; changes ride
   the modification flow with regression review.
5. Modifications change only what the delta lists; snapshot the prior version to
   `revisions/` first.
6. **A user story arriving IS the build instruction** (owner directive, 2026-07-19).
   Receiving a story in any form means: create/extend the feature in
   `features/features.js`, build its UI reference, ship `COMPONENTS.md` — no
   confirmation, no questions back.
7. **Three designs per story:** every user story ships **three genuinely different
   design variants** in one reference page behind a variant switcher (Design A · B · C)
   for the client to choose from. After approval, the chosen variant remains and the
   others are removed.
8. **References are working products, not mockups:** every interaction the story's
   acceptance criteria describe must actually function — live flows, enabled/disabled
   validations, state changes, toasts, empty/error states. If the client can click it
   in the real product, they can click it in the reference.
9. **Product UI only inside the reference:** never add reviewer notes, "system-behaviour"
   blocks, meta commentary, **or simulation/testing controls of any kind** (e.g. a
   "simulate save failure" switch) inside the reference page. Response-dependent states
   (API success/failure toasts, network errors) are NOT demonstrated interactively — the
   frontend developer wires them from the user story at API-integration time; leave a
   code comment marking the branch and its exact copy. Non-visual acceptance criteria are
   documented in the story's `COMPONENTS.md`, never on the artifact.
10. **Client artifact delivery protocol** (docs/07 §5): after every delivered story, remind
    the BA to flag when the feature's business is complete; when she does, ask which
    feature to package; when she names it, publish a self-contained shareable artifact of
    that feature's reference(s) only, and return the link(s).
11. **Related enhancement vs new feature — where the design lives** (owner directive
    2026-07-22). Before building a story, decide:
    - **A change/addition to an area that already has a product page** (e.g. a new
      column/filter on Booking, a field on Scheduling) → build it **inside that product
      page**, not as a standalone Features-accordion entry. **Every newly-added element
      MUST carry both: (1) a persistent soft-green tint `background` (via
      `data-new="<feature-id>"`, styled in `components.css`), and (2) a `.badge--new`
      ("New") label on its header/label.** This green-background-plus-label treatment is
      the standard, always-visible "this is new inside an existing feature" marker — it is
      NOT hidden behind a mode. Additionally the page supports a stronger
      **`?whatsnew=<feature-id>` review mode** (dashed ring on every `[data-new]` + a
      dismissible banner naming the story) for focused BA/client review. Record the
      enhancement in the product page's `COMPONENTS.md` and remove it from
      `features/features.js`.
    - **A genuinely new capability/screen** with no existing product page → stays a
      normal entry in the Features accordion (`features/features.js`), per §4.1.
    Marker CSS in `components.css`: `.badge--new` (green pill, no dot),
    `[data-new]` tint (`.data-table th/td[data-new]` and `.field[data-new]`),
    `.is-whatsnew [data-new]` ring, `.whatsnew-banner`. No Super Admin enhancement
    exists yet; the worked example lives in the Partner system ("Bookings Check-in
    Audit" in its `bookings.html`). Where each Super Admin page comes from:
    `design-system/docs/product-pages/README.md`.

## 5. Token optimization

1. Load context in this order and stop as soon as the task is covered:
   this file → registry index → only the entries/patterns/layouts the task touches.
2. Never process the entire Design System when a few components suffice. Never read whole
   stylesheets for orientation — registry frontmatter (`css-classes`, `status`, `related`)
   exists precisely to avoid that.
3. In long sessions, don't re-load files already in context.

## 6. After a component is approved

Automatically recommend (and on request, perform) updates to all seven targets:
**Component Registry · Pattern Library · Documentation · Version (semver per
`docs/03-governance-workflow.md` §6) · Changelog (`docs/05-CHANGELOG.md`) · AI Prompt
Library (`docs/04-ai-prompts.md`) · Governance docs** (if process changed).

## 7. Quality bar

Comparable to IBM Carbon, Atlassian, Shopify Polaris, Microsoft Fluent. Priorities, in
order: **maintainability, consistency, scalability, accessibility, AI-readability** — over
visual creativity. When a trade-off appears, the boring, consistent option wins.

## 8. Delivery pipeline (repo → production)

Same pipeline as the Partner system (static site → nginx Docker image → Caddy), with its
own names: image `<DOCKER_USERNAME>/superadmin-web-design-system:prod`, container
`superadmin-web-design-system-prod` on the `base` network. The hostname and the
GitHub repo/secrets are not set up yet — add them here once they exist.

**Access:** pages authenticate against the same Design System Access backend
(`/api/design-system/login` · `/me`). This deck is the backend's **`superadmin`
system** (`SYSTEM` in `assets/js/api.js`) — the system and its page keys must exist in
the Super Admin dashboard (Design System → Design Systems / Design System Pages) before
anyone can sign in. The key list lives in `design-system/docs/11-page-permissions.md` and
in `NAV_PERM` (`assets/shell.js`); keep the two identical.

## 9. Brand identity (LOCKED values — the Super Admin's own identity)

The Super Admin keeps **its current dashboard colours**. Values were read from
`HighFive-SuperAdmin-Front/src/_metronic/assets/sass/` (custom.css, _variables*.scss).
Per §3.2 they live **only** in the Tier-1 layer of `tokens.css`. Token names keep the
Partner system's historical `--lime-*` names so `components.css` works unchanged — the
values are orange.

**Light-first** (the dashboard's default theme; dark is a remap).

| Role                          | Value                               |
|-------------------------------|-------------------------------------|
| **Primary — Orange**          | `#FC6404` (`--lime-500`)            |
| Primary hover / pressed       | `#E05400` / `#B84300`               |
| Primary as text (light)       | `#B84300` (`--lime-700`, AA on white) |
| Text on primary               | `#FFFFFF`                           |
| Canvas (light)                | `#FCFCFC`                           |
| Surface (light)               | `#FFFFFF`                           |
| Text (light)                  | `#071437` (gray-900)                |
| Text secondary / tertiary     | `#4B5675` / `#78829D`               |
| Border / divider              | `#DBDFE9` / `#E4E6EF`               |
| Sidebar (light)               | `#FFFFFF`, hover `#F7F8FB`           |
| Canvas + sidebar (dark)       | `#131313`                           |
| Surface (dark)                | `#1C1C1C`                           |

Typography: **Inter** (English) · **Tajawal** (Arabic) — the dashboard's own pair.
Arabic is first-class; RTL is never an afterthought (§3.3).

Status colours keep the shared accessible semantic palette (not Metronic's defaults), so a
status means the same thing in the Partner and Super Admin systems.

**Logo**: the same 5-finger HighFive mark, recoloured automatically through the
`--lime-*` tokens; the header sub-label reads "HighFive Super Admin".
